# Design

## 2026-11-16: replica-owned live subscriptions

The service has no DB. A RabbitMQ classic queue is server-named, exclusive, auto-delete, 1000 messages / 4 MiB, TTL 30 seconds, drop-head. Each replica binds its own queue to `incidents.live`, `content.live`, and `notifications.live` only for subscriptions on that replica. It binds `control.#` from `auth.live` and `projects.live` at startup. Reference counts keep a shared key bound once; unbind is delayed 20 seconds after the final subscriber disconnects.

For an investigation, the order is: obtain its project from incidents using the user's token, check `project.read`, register the local buffer, bind the key and await broker confirmation, fetch paginated events after the client's sequence, merge buffered live events by sequence, then send `subscription.ack`. A gap stops the subscription. The client can reconnect and replay from its last applied sequence. Project events have no global sequence and trigger a REST refresh.

JWTs are checked locally against auth JWKS and a live auth session key. Project rights use `aiip-kit`'s `DragonflyAccessChecker`, with a service-token-backed fallback to `projects`. Rights are checked on subscribe, delivery, and every five seconds. Control events close affected sockets early. Dragonfly Lua keeps at most two active leases per session; every five seconds renews the connection lease. Sockets last 30–60 minutes with jitter. Loss of the broker sends `resync_required` and recreates the queue and bindings.

Investigation replay checks the session and project right again after the history request, before sending any events. A failed bind releases only bindings that were confirmed. `control.member.removed` and `control.role.changed` target the named user; `control.project.deleting` closes every subscriber of the project. Lease renewal rejects an entry whose own expiry has passed, even if the sorted-set key still exists.

The live routing keys follow `backend/messaging.md`: `project.<project_id>`, `project.<project_id>.investigation.<investigation_id>`, and `user.<user_id>` on `*.live`. `backend/services/realtime.md` has older examples naming `*.events` and `investigation.<id>`; those conflict with the broker contract, so the latter wins. The producer exchanges must exist before startup because realtime declares them passively.

Alternative considered: a shared queue across replicas. That would load-balance each event to one replica and miss sockets on the others. A durable queue per replica would keep stale queues after crashes and accumulate events with no clients. Exclusive auto-delete queues match the live/replay contract.

## Open integration points

The current implementation expects auth and projects to issue service credentials and the live producer exchanges to be declared. A temporary two-replica RabbitMQ/Dragonfly integration test verifies separate queues, routing, control revocation, lease limits, and queue auto-delete. The same test drives `/ws/v1/events` through ASGI with a signed cookie and allowed Origin, checks rejected handshakes, subscribes, receives the ack and a live event, disconnects, and reconnects. A reverse-proxy network handshake and deployment in k3d remain to be run. The `EventsPage.next_cursor` field is treated as a signal to continue by `after_sequence`; if incidents uses an opaque cursor instead, the replay adapter must be aligned with that API before deployment.

Live queue overflow at the broker uses drop-head. RabbitMQ silently removes the oldest queued messages; the consumer receives neither a gap marker nor an overflow notification. Investigation sequence gaps trigger `resync_required`. Project and inbox events have no stream sequence or revision, so a delivered event cannot prove that earlier events were missed, and loss of the final event can leave the browser stale indefinitely while the socket stays connected. `resync_required` covers detected broker disconnection and gateway buffer overflow, not broker-side drop-head. Clients must periodically re-fetch project lists and inbox counts through the owners' REST endpoints even while connected; reconnect and broker-loss re-fetches are additional recovery points. A reliable on-demand gap detector requires a monotonic stream revision in those producer contracts (or an explicit broker overflow signal), which realtime cannot synthesize from the current messages.
